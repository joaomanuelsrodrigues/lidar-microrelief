## 1. Ground filtering

The pipeline uses a progressive morphological filter over the common-grid per-cell minimum elevation surface:

> “A progressive morphological filter … open the minimum surface with windows of growing size and mark as object any cell that the opening pushes down further than a slope-dependent tolerance allows.”  
> [ground.py:3](src/microrelief/ground.py:3)

For each window, it performs a grey opening and rejects cells whose elevation above the opening exceeds:

\[
\min(s\cdot w + dh_0,\ dh_{\max})
\]

This is implemented at [ground.py:87](src/microrelief/ground.py:87):

> `opened = grey_opening(...)`  
> `tolerance = min(params.slope_threshold * window_m + params.elevation_threshold_m, params.max_elevation_m)`  
> `is_object |= (surface - opened) > tolerance`

The shipped run used:

- Cell size: `0.5 m`
- `max_window_m = 4.0`
- `slope_threshold = 0.3`
- `elevation_threshold_m = 0.3 m`
- `max_elevation_m = 3.5 m`

These are recorded at [provenance.json:86](viewer/provenance.json:86).

Despite its name, `max_window_m=4.0` produces widths `1.5, 2.5, 4.5 m`, because radii double and the width is `(2r+1)cell`:

> “`max_window_m` is a ceiling on the radius search and not a width that is ever used.”  
> [ground.py:55](src/microrelief/ground.py:55)

Why those values:

- The exact reasons for `max_window_m=4.0`, `slope_threshold=0.3`, and `elevation_threshold_m=0.3` are not established by the code or run outputs. The run explicitly labels all three uncalibrated at [provenance.json:96](viewer/provenance.json:96).
- The code does explain `max_elevation_m=3.5`: the tallest verified site riser was 2.98 m, while 3.0 m was only 2 cm above it and inside the stated 0.2–0.3 m error band. See [cli.py:318](src/microrelief/cli.py:318).
- At the default windows, the cap is not reached: the largest tolerance is `0.3×4.5+0.3 = 1.65 m`. This follows directly from the formula and recorded parameters.

Agreement is calculated only over cells containing at least one retained return; official ground means at least one ASPRS class-2 return in that cell ([ground.py:137](src/microrelief/ground.py:137)).

| Official class | Pipeline recall | Majority-class null |
|---|---:|---:|
| Ground | 0.9992618534 | 0.5034972851 |
| Non-ground | 0.4953807915 | 0.5034972851 |

Overall accuracy is `0.7490835382`. The underlying counts are `tp=7,809,752`, `fn=5,769`, `tn=3,817,874`, and `fp=3,889,074`, from [provenance.json:2](viewer/provenance.json:2).

The null is the accuracy obtained by always predicting the prevalent official class:

> `majority_class_null=max(prevalence, 1.0 - prevalence)`  
> [ground.py:150](src/microrelief/ground.py:150)

## 2. Common grid

The grid is defined by `Grid` and `grid_for_bounds()` in [grid.py:22](src/microrelief/grid.py:22). Bounds are snapped outward to the cell lattice at [grid.py:79](src/microrelief/grid.py:79).

The shipped grid is:

- EPSG:3763
- Origin `(-20990.0, 256990.0)`
- `3960 × 3960`
- `0.5 m` cells

See [provenance.json:19](viewer/provenance.json:19).

There are no per-tile raster windows to combine. One `Accumulator` is allocated from this grid, and every tile’s points are mapped directly into its flat cell indices:

> “Folds tiles into one grid’s worth of per-cell statistics.”  
> [accumulate.py:72](src/microrelief/accumulate.py:72)

The relevant operations update the common arrays by common-grid cell index:

> `self._min_all[cells] = ...`  
> `self._max_all[cells] = ...`  
> `self._n_all[cells] += counts`  
> [accumulate.py:103](src/microrelief/accumulate.py:103)

After each tile, only these grid aggregates survive; no tile array is retained:

> “`add()` … returns having copied nothing of the batch’s arrays into `self`—only per-cell aggregates … survive.”  
> [accumulate.py:72](src/microrelief/accumulate.py:72)

Thus the repository structurally excludes elementwise arithmetic between per-tile windows: it never constructs such windows. All later elementwise operations are between arrays with `grid.shape`, and export uses that same grid’s dimensions, CRS, and transform ([export.py:47](src/microrelief/export.py:47)).

## 3. Voids

The shipped DTM basis fractions are:

- Measured: `0.7460224722` — 74.6022%
- Interpolated: `0.2520743419` — 25.2074%
- Undetermined: `0.0019031859` — 0.1903%

See [provenance.json:27](viewer/provenance.json:27).

A cell is measured only if the filter calls it ground and it has at least `k_min_returns`; otherwise it is interpolated only if a measured neighbour lies within 2 m:

> `measured = is_ground & (stats.n_all >= k_min_returns)`  
> `within = ... <= d_max_interp_m`  
> [density.py:65](src/microrelief/density.py:65)

The closed-form null assumes Poisson arrivals:

\[
P(N=0)=e^{-\lambda},\qquad
\lambda=\rho c^2f
\]

implemented at [precheck.py:34](src/microrelief/precheck.py:34).

For the run, `ρ = 26.9902122232 pts/m²`, `c = 0.5 m`, and the honesty report deliberately uses `f=1` ([density.py:91](src/microrelief/density.py:91)):

\[
e^{-26.9902122232(0.5)^2}
= e^{-6.7475530558}
=0.0011737482
\]

Therefore the expectation is `0.1173748%`, recorded at [provenance.json:28](viewer/provenance.json:28).

This is a no-return reference expectation, not a prediction of the pipeline’s measured-basis fraction: the latter also reflects canopy interception and ground-filter rejection.

## 4. Provenance and reproducibility

Do two runs produce identical bytes? Only in limited demonstrated cases.

- The synthetic export test writes the same surfaces twice and compares SHA-256 digests for every raster; they match ([test_export.py:152](tests/test_export.py:152)).
- Two clean real-data passes were observed to be byte-identical, but real-data replay is explicitly not established. The shipped record reports a corrupted read and a failed read and says the root cause remains open ([provenance.json:76](viewer/provenance.json:76)).
- The complete provenance files cannot be byte-identical across ordinary runs because `created_utc` changes. The timestamp is intentionally omitted from the reproducibility hash ([provenance.py:130](src/microrelief/provenance.py:130)).
- Cross-machine replay is unverified ([provenance.json:80](viewer/provenance.json:80)).

Can a stranger reproduce from the record alone? No. The code itself says the record lacks both the acquisition route and exact code revision:

> “not the acquisition route or the exact code revision, so it is a verification anchor, not a self-contained recipe”  
> [provenance.py:3](src/microrelief/provenance.py:3)

It supplies file basenames and SHA-256 digests, grid, parameters, and package version, but the hash sees code only through the version. The record warns that version bumping is not enforced ([provenance.json:81](viewer/provenance.json:81)).

Does CC-BY attribution reach the consumer? Yes for the exported products and bundled viewer:

- The complete attribution string is in the provenance artifact at [provenance.json:14](viewer/provenance.json:14).
- Export attaches it to every GeoTIFF’s metadata tags ([export.py:39](src/microrelief/export.py:39)).
- A test opens every exported band independently and checks for `CC BY 4.0` ([test_export.py:143](tests/test_export.py:143)).
- The viewer loads and displays `p.attribution` from `provenance.json` ([index.html:49](viewer/index.html:49)).
