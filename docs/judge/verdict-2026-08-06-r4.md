## 1. Ground filtering

The pipeline uses a progressive morphological filter over the per-cell minimum elevation surface:

> “A progressive morphological filter … open the minimum surface with windows of growing size” — [ground.py:1](src/microrelief/ground.py:1)

For each window, it performs a grey opening and rejects cells whose elevation above the opening exceeds

\[
\min(slope\_threshold \times window\_width + elevation\_threshold,\ max\_elevation).
\]

That implementation is at [ground.py:87](src/microrelief/ground.py:87):

> `tolerance = min(params.slope_threshold * window_m + params.elevation_threshold_m, params.max_elevation_m)`

The recorded run parameters are:

- cell size: `0.5 m`
- `max_window_m = 4.0`
- `slope_threshold = 0.3`
- `elevation_threshold_m = 0.3 m`
- `max_elevation_m = 3.0 m`

See [provenance.json:84](viewer/provenance.json:84).

At 0.5 m resolution, `max_window_m=4.0` actually produces windows of 1.5, 2.5, and 4.5 m; the parameter is a ceiling on a doubling radius search, not an actual maximum width. This is asserted at [test_ground.py:94](tests/test_ground.py:94):

> `windows_for(4.0, 0.5) == windows_for(6.0, 0.5) == (1.5, 2.5, 4.5)`

Why these values:

- `0.5 m` matches the finest DGT product resolution ([CALIBRATIONS.md:8](CALIBRATIONS.md:8)).
- The two `0.3` thresholds are literature-derived starting values and explicitly remain uncalibrated ([CALIBRATIONS.md:15](CALIBRATIONS.md:15), [provenance.json:94](viewer/provenance.json:94)).
- `max_window_m=4.0` is also an unmeasured default intended to set the object-removal scale ([CALIBRATIONS.md:14](CALIBRATIONS.md:14)).
- `max_elevation_m=3.0` is justified only on the synthetic hillside: it preserves all five terrace levels ([test_ground.py:39](tests/test_ground.py:39), [test_ground.py:49](tests/test_ground.py:49)); reducing the cap below one synthetic riser causes substantial damage ([test_ground.py:56](tests/test_ground.py:56)). It is not calibrated against a measured Sistelo riser.

Agreement is computed per measured cell against whether that cell contains at least one official ASPRS class-2 return ([ground.py:137](src/microrelief/ground.py:137)).

| Official class | Recall | Majority-class null |
|---|---:|---:|
| Ground | 0.9992619 | 0.5034973 |
| Non-ground | 0.4953808 | 0.5034973 |

Overall accuracy is `0.7490835`. Exact recorded values are at [provenance.json:2](viewer/provenance.json:2). The null is one overall constant—`max(class prevalence, 1−prevalence)`—rather than a separately calculated null for each class ([ground.py:150](src/microrelief/ground.py:150)).

## 2. Common grid

The grid is defined by `Grid` and `grid_for_bounds()` in [grid.py:22](src/microrelief/grid.py:22) and [grid.py:65](src/microrelief/grid.py:65). Bounds are snapped outward to the cell lattice:

> `origin_x = floor(minx / cell) * cell`  
> `origin_y = ceil(maxy / cell) * cell`

The run constructs one grid before reading any tile ([cli.py:208](src/microrelief/cli.py:208)) and passes that same object into a single accumulator.

There are no per-tile raster windows. Each tile is immediately mapped to flat indices of that common grid and folded into global minimum, maximum, and count arrays ([accumulate.py:91](src/microrelief/accumulate.py:91)). As its class contract says:

> “only per-cell aggregates (indexed by grid cell, not by point) survive” — [accumulate.py:72](src/microrelief/accumulate.py:72)

`finish()` reshapes only those common arrays to the common grid shape ([accumulate.py:114](src/microrelief/accumulate.py:114)). All subsequent elementwise operations consume those arrays—for example, DTM/DSM/CHM construction at [surfaces.py:46](src/microrelief/surfaces.py:46). Thus code inspection shows no representation on which elementwise per-tile-window arithmetic could occur.

## 3. Voids

The machine-readable run record reports:

- measured: `0.7460224722` — 74.602%
- interpolated: `0.2520743419` — 25.207%
- undetermined: `0.0019031859` — 0.190%

See [provenance.json:27](viewer/provenance.json:27).

A cell is measured only when the filter calls it ground and its return count reaches `k_min_returns`; otherwise it is interpolated only if a measured cell is within 2 m ([density.py:56](src/microrelief/density.py:56)).

The closed form implemented by the repository is

\[
P(N_{\rm ground}=0)=e^{-\rho a f}
=e^{-\rho c^2f}.
\]

See [precheck.py:34](src/microrelief/precheck.py:34).

For the honesty report, the code deliberately sets `f=1` ([density.py:91](src/microrelief/density.py:91)). With recorded density `ρ=26.9902122 pts/m²` and `c=0.5 m`:

\[
e^{-26.9902122(0.5)^2}=0.0011737482,
\]

or `0.1174%`, matching [provenance.json:28](viewer/provenance.json:28).

The empirical counterpart to “zero ground evidence” is measured emptiness, `interpolated + undetermined = 25.3978%`, not merely the final `0.1903%` left undetermined after interpolation.

## 4. Provenance and reproducibility

Do two runs produce identical bytes? Qualified answer:

- Synthetic exports are byte-identical on the tested machine; the test hashes every raster from two exports and compares them ([test_export.py:152](tests/test_export.py:152)).
- Cross-machine equality is explicitly unverified because bytes depend on GDAL/libdeflate builds ([test_export.py:198](tests/test_export.py:198)).
- Real-data replay is not established: four reads yielded two clean byte-identical results, one corrupted-coordinate result, and one I/O failure ([live-smoke.md:204](docs/live-smoke.md:204)).

So an unconditional “yes” is not supported.

Can a stranger reproduce from the record alone? No. The record contains basenames and SHA-256 values but no source/download locator ([provenance.py:33](src/microrelief/provenance.py:33), [provenance.json:34](viewer/provenance.json:34)). It also records only the package version, not a commit digest or the GDAL/libdeflate/runtime versions. Indeed, the repository records that a code change without a version bump can reuse the same reproducibility hash ([live-smoke.md:195](docs/live-smoke.md:195)). The repository plus separately acquired inputs may support reconstruction; the provenance JSON alone does not.

Does attribution reach the consumer? Yes for a consumer holding any exported GeoTIFF. The attribution string includes DGT, CC BY 4.0, derivation, and non-endorsement ([provenance.py:22](src/microrelief/provenance.py:22)). `export()` writes it into every raster’s metadata tags ([export.py:39](src/microrelief/export.py:39), [export.py:47](src/microrelief/export.py:47)), and the test opens every band independently and verifies the tag ([test_export.py:143](tests/test_export.py:143)).

## 5. Refusals

Three concrete refused inputs, with the reason carried in the exception message:

1. LAS/LAZ with no resolvable CRS:

   > `declares no CRS; refusing to assume one`  
   > `CRS could not be resolved to an EPSG code; refusing to assume one`

   [read.py:69](src/microrelief/read.py:69)

2. A file containing a non-finite coordinate:

   > `point(s) have non-finite {name} ...; refusing to build a surface on it`

   [read.py:108](src/microrelief/read.py:108)

3. A return outside the catalogue-declared tile footprint:

   > `A return cannot be outside the box the catalogue derived from the returns, so this is a corrupted read, not a property of the terrain — refusing rather than publishing a density divided by an exploded bounding box`

   [read.py:137](src/microrelief/read.py:137)

These are exercised by repository tests, including the non-finite-coordinate refusal at [test_read.py:80](tests/test_read.py:80) and footprint refusal at [test_read.py:188](tests/test_read.py:188).

## README contradictions

1. The README says the official classification “enters the comparison … and nowhere else” ([README.md:7](README.md:7)). In fact, input acceptance also depends on it: a file without ASPRS class 2 is refused before comparison ([read.py:116](src/microrelief/read.py:116)).

2. The README says transparent cells in “DTM/DSM/CHM are undetermined” ([README.md:14](README.md:14)). The code gives the bands different validity rules:

   - DTM is present for measured and interpolated cells.
   - DSM is present wherever any return exists, independently of basis.
   - CHM is present only for measured-ground cells.

   See [surfaces.py:37](src/microrelief/surfaces.py:37). Consequently, an interpolated cell can be transparent in DSM or CHM without being undetermined, and an undetermined cell containing a rejected return can have a visible DSM.

3. The README says the `0.117%` empty-cell expectation should be read beside the measured `0.2% undetermined` ([README.md:40](README.md:40)). The formula predicts cells with zero ground returns before interpolation ([precheck.py:34](src/microrelief/precheck.py:34)). Its empirical counterpart is therefore the entire non-measured share—interpolated plus undetermined, approximately `25.4%`—not only the residual `0.2%` that remains undetermined after the 2 m fill.
