## 1. Ground filtering

The pipeline uses a progressive morphological filter over the per-cell minimum elevation surface. Successively larger morphological openings lower local objects; a cell is rejected when the difference exceeds a slope-dependent, capped tolerance ([ground.py:1](src/microrelief/ground.py:1), [ground.py:87](src/microrelief/ground.py:87)):

\[
t(w)=\min(0.3w+0.3,\ 3.5)\text{ metres}
\]

The committed run parameters are ([provenance.json:86](viewer/provenance.json:86)):

- `max_window_m = 4.0`
- `slope_threshold = 0.3`
- `elevation_threshold_m = 0.3 m`
- `max_elevation_m = 3.5 m`

At 0.5 m resolution, `max_window_m=4` produces actual widths of 1.5, 2.5, and 4.5 m; it is a ceiling on the radius search, not an attained width ([ground.py:46](src/microrelief/ground.py:46), [test_ground.py:94](tests/test_ground.py:94)). Thus the largest tolerance actually reached in this run is \(0.3(4.5)+0.3=1.65\) m, below the 3.5 m cap.

Why those values:

- The repository outputs support the 3.5 m cap: the tallest verified terrace riser was 2.98 m ([riser-measurement.md:129](docs/riser-measurement.md:129)); 3.5 m clears that riser plus the stated 0.2–0.3 m measurement band while remaining below verified 4.6–6.5 m built walls ([riser-measurement.md:151](docs/riser-measurement.md:151)).
- Synthetic tests show that a cap above a 1.5 m riser preserves all five terrace levels, while lowering it below the riser damages the terrace ([test_ground.py:33](tests/test_ground.py:33), [test_ground.py:56](tests/test_ground.py:56)).
- A code/output-supported empirical reason for selecting exactly `4.0`, `0.3`, and `0.3` is not available. Indeed, the run record labels all three—and, inconsistently, the calibrated cap—as uncalibrated ([cli.py:35](src/microrelief/cli.py:35), [provenance.json:96](viewer/provenance.json:96)).

Agreement is per measured cell against presence of at least one official ASPRS class-2 return ([ground.py:137](src/microrelief/ground.py:137)). The committed result is:

| Official class | Recall | Majority-class null |
|---|---:|---:|
| Ground | 0.9992618534 | 0.5034972851 |
| Non-ground | 0.4953807915 | 0.5034972851 |

Values: [provenance.json:2](viewer/provenance.json:2).

The null is one overall always-predict-the-majority accuracy, `max(prevalence, 1-prevalence)` ([ground.py:150](src/microrelief/ground.py:150)). The same value is therefore shown beside both classes; the repository does not calculate distinct class-specific recall nulls. Overall accuracy is 0.7490835382.

## 2. Common grid

The grid representation is `Grid`, with its origin, cell size, dimensions, CRS, transform, and shape defined at [grid.py:22](src/microrelief/grid.py:22). `grid_for_bounds()` snaps the AOI outward and calculates the dimensions at [grid.py:65](src/microrelief/grid.py:65).

The actual grid is 3960 × 3960, 0.5 m, EPSG:3763, with origin `(-20990, 256990)` ([provenance.json:19](viewer/provenance.json:19)).

There are no production per-tile raster windows:

1. The grid is constructed once from the AOI before reading the inputs ([cli.py:213](src/microrelief/cli.py:213)).
2. One `Accumulator(grid)` allocates global arrays of `grid.n_cells` ([accumulate.py:81](src/microrelief/accumulate.py:81)).
3. Every tile’s point coordinates are immediately mapped into that grid ([accumulate.py:91](src/microrelief/accumulate.py:91)).
4. Only common-grid extrema and counts survive `add()` ([accumulate.py:103](src/microrelief/accumulate.py:103)).
5. The only cross-surface elementwise subtraction, CHM = DSM − DTM, happens afterward on arrays initialized with `grid.shape` ([surfaces.py:48](src/microrelief/surfaces.py:48), [surfaces.py:62](src/microrelief/surfaces.py:62)).

Thus, for this repository version, elementwise arithmetic between per-tile windows cannot occur because no such raster-window representation is created.

## 3. Voids

The committed DTM basis fractions are ([provenance.json:27](viewer/provenance.json:27)):

- Measured: `0.7460224722` = **74.6022%**
- Interpolated: `0.2520743419` = **25.2074%**
- Undetermined: `0.0019031859` = **0.1903%**

A cell is measured only when the filter calls it ground and it has at least `k_min_returns`; otherwise it is interpolated only if a measured cell is within 2 m ([density.py:56](src/microrelief/density.py:56)). Beyond that it remains undetermined.

The closed-form empty-cell expectation is Poisson:

\[
P(N=0)=e^{-\lambda},\qquad
\lambda=\rho c^2 f
\]

as implemented at [precheck.py:34](src/microrelief/precheck.py:34). The honesty report deliberately uses \(f=1\) ([density.py:91](src/microrelief/density.py:91)). With \(\rho=26.9902122232\) points/m² and \(c=0.5\) m:

\[
e^{-26.9902122232(0.5)^2}
=0.001173748206
=\mathbf{0.117375\%}.
\]

This is the null expectation for cells containing zero returns if every return reached ground. It is not an expectation for the final 2 m interpolation-based undetermined fraction.

## 4. Provenance and reproducibility

**Do two runs produce identical bytes?** A qualified yes, not a general guarantee.

- Two clean 0.3.0 runs on the real data were byte-identical across all six GeoTIFF bands; their records matched after excluding `created_utc` ([live-smoke.md:308](docs/live-smoke.md:308), [live-smoke.md:334](docs/live-smoke.md:334)).
- Synthetic exports also have a direct two-run byte-identity test ([test_export.py:152](tests/test_export.py:152)).
- But real-data stability is explicitly not established: an earlier four-read session included one corrupt read and one failed read ([live-smoke.md:204](docs/live-smoke.md:204)); the committed provenance retains that limitation ([provenance.json:76](viewer/provenance.json:76)).
- The sidecar itself cannot be literally byte-identical across ordinary runs because `created_utc` is generated from the current time ([provenance.py:130](src/microrelief/provenance.py:130)).

**Can a stranger reproduce from the record alone?** No. The code explicitly calls it a verification anchor rather than a self-contained recipe because it omits the acquisition route and exact code revision ([provenance.py:1](src/microrelief/provenance.py:1)). It records input basenames and hashes but not download URLs ([provenance.py:39](src/microrelief/provenance.py:39)). Code enters the hash only through the package version ([provenance.py:114](src/microrelief/provenance.py:114)).

**Does CC-BY attribution reach the consumer?** Yes for each exported GeoTIFF and for the provenance sidecar:

- Attribution text: [provenance.py:27](src/microrelief/provenance.py:27)
- Inserted in the tags of every exported raster: [export.py:39](src/microrelief/export.py:39), [export.py:47](src/microrelief/export.py:47)
- Independently tested for every band: [test_export.py:143](tests/test_export.py:143)
- Present in the committed sidecar: [provenance.json:14](viewer/provenance.json:14)

The repository does not establish embedded attribution in the standalone viewer PNG files.

   Code and message at [read.py:116](src/microrelief/read.py:116):

   Code and message at [read.py:128](src/microrelief/read.py:128):

   > `<file>: <n> return(s) fall outside its declared footprint … A return cannot be outside the box the catalogue derived from the returns, so this is a corrupted read, not a property of the terrain — refusing rather than publishing a density divided by an exploded bounding box`

## README contradictions

I found two contradictions:

1. **Calibrated cap versus published “uncalibrated” status.**  
   README lines 81–85 call `max_elevation_m=3.5` “site-calibrated” ([README.md:78](README.md:78)). But production code still includes `max_elevation_m` in `UNCALIBRATED` ([cli.py:35](src/microrelief/cli.py:35)), and the committed run publishes it as uncalibrated ([provenance.json:96](viewer/provenance.json:96)).

2. **Byte-identical “record” without the timestamp qualification.**  
   README lines 109–110 say the second pass is byte-identical across “all six bands and the record” ([README.md:109](README.md:109)). The actual output record says “the record minus `created_utc`” ([live-smoke.md:334](docs/live-smoke.md:334)), and code generates a fresh timestamp on every run ([provenance.py:130](src/microrelief/provenance.py:130)). Therefore the complete provenance JSON files are not byte-identical.
