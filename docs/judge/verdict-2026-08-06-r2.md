## 1. Ground filtering

The pipeline uses its own progressive morphological filter over the per-cell minimum elevation surface:

> “open the minimum surface with windows of growing size and mark as object any cell that the opening pushes down further than a slope-dependent tolerance allows.”  
> — [ground.py](src/microrelief/ground.py:3)

The production record gives these parameters:

| Parameter | Value |
|---|---:|
| Cell size | 0.5 m |
| `max_window_m` | 4.0 m |
| `slope_threshold` | 0.3 |
| `elevation_threshold_m` | 0.3 m |
| `max_elevation_m` | 3.0 m |
| `k_min_returns` | 1 |
| `d_max_interp_m` | 2.0 m |

Evidence: [provenance.json](viewer/provenance.json:84).

At 0.5 m, `max_window_m=4` actually generates 1.5, 2.5 and 4.5 m windows because the radius doubles:

> `assert windows_for(4.0, 0.5) == windows_for(6.0, 0.5) == (1.5, 2.5, 4.5)`  
> — [test_ground.py](tests/test_ground.py:94)

Why these values? A site-specific justification is not answerable from the repository. The output explicitly lists all seven parameters as uncalibrated: [provenance.json](viewer/provenance.json:94).

There is only partial synthetic justification:

- With the 3 m cap, all five synthetic terrace levels survive: [test_ground.py](tests/test_ground.py:39).
- Lowering the cap below one 1.5 m riser damages the terraces: [test_ground.py](tests/test_ground.py:56).
- High synthetic canopy returns are mostly rejected: [test_ground.py](tests/test_ground.py:101).

That demonstrates fixture behavior, not that the values are calibrated for Sistelo.

Agreement is computed against per-cell presence of official ASPRS class 2:

> `official = (stats.n_ground_asprs > 0)[measured]`  
> — [ground.py](src/microrelief/ground.py:141)

| Official class | Recall | Overall majority-class null |
|---|---:|---:|
| Ground | 0.9992618534 | 0.5034972851 |
| Non-ground | 0.4953807915 | 0.5034972851 |

Overall accuracy is 0.7490835382, with TP 7,809,752; FN 5,769; TN 3,817,874; FP 3,889,074: [provenance.json](viewer/provenance.json:2).

There are not separate per-class nulls. The single null is:

> `max(prevalence, 1.0 - prevalence)`  
> — [ground.py](src/microrelief/ground.py:150)

It is an accuracy baseline, not a baseline for either recall.

## 2. Common grid

`Grid` defines origin, cell size, dimensions and CRS at [grid.py](src/microrelief/grid.py:22). `grid_for_bounds()` constructs it, snapping the extent outward at [grid.py](src/microrelief/grid.py:65).

The recorded production grid is 3960 × 3960 at 0.5 m, EPSG:3763, origin `(-20990, 256990)`: [provenance.json](viewer/provenance.json:19).

The complete production path provides structural evidence that no per-tile raster arithmetic occurs:

1. One grid is constructed before reading any inputs: [cli.py](src/microrelief/cli.py:208).
2. One accumulator is constructed around that grid: [cli.py](src/microrelief/cli.py:165).
3. Every tile’s coordinates are mapped directly to that grid: [accumulate.py](src/microrelief/accumulate.py:91).
4. Only common-grid extrema and counts survive each tile:

> `self._min_all[cells] = np.minimum(...)`  
> `self._max_all[cells] = np.maximum(...)`  
> `self._n_all[cells] += counts`  
> — [accumulate.py](src/microrelief/accumulate.py:103)

5. Surface arithmetic occurs only after those arrays are reshaped to the common grid: [accumulate.py](src/microrelief/accumulate.py:114), [surfaces.py](src/microrelief/surfaces.py:37).

There is no per-tile raster-window representation in the production path, so there is nothing on which elementwise cross-window arithmetic could operate.

## 3. Voids

The committed output reports:

| Basis | Fraction | Percent |
|---|---:|---:|
| Measured | 0.7460224722 | 74.6022% |
| Interpolated | 0.2520743419 | 25.2074% |
| Undetermined | 0.0019031859 | 0.1903% |

Evidence: [provenance.json](viewer/provenance.json:27).

A measured cell must both pass the ground filter and meet the return-count threshold. Other cells are interpolated only when a measured neighbour is within 2 m; otherwise they remain undetermined: [density.py](src/microrelief/density.py:56).

The closed form is:

\[
P(N=0)=e^{-\lambda}, \qquad \lambda=\rho c^2f
\]

implemented as:

> `lam = density_pts_m2 * cell * cell * ground_fraction`  
> `return math.exp(-lam)`  
> — [precheck.py](src/microrelief/precheck.py:34)

The honesty report deliberately uses \(f=1\): [density.py](src/microrelief/density.py:91).

With \(\rho=26.9902122232\) points/m² and \(c=0.5\) m:

\[
e^{-26.9902122232(0.5)^2}
=0.0011737482
=0.117375\%.
\]

That exact result is recorded at [provenance.json](viewer/provenance.json:28). It is a Poisson null assuming every return reaches the ground—not an expectation for the final, post-interpolation `undetermined` class.

## 4. Provenance and reproducibility

Do two runs produce identical bytes? Not as an unqualified claim.

- A synthetic test demonstrates identical GeoTIFF bytes when the same already-created provenance object is exported twice: [test_export.py](tests/test_export.py:152).
- Golden GeoTIFF hashes are machine-local; the test says they depend on GDAL/libdeflate and cross-machine replay is unverified: [test_export.py](tests/test_export.py:198).
- A complete fresh run also creates a new `created_utc` timestamp: [provenance.py](src/microrelief/provenance.py:124). Therefore its `provenance.json` bytes will differ even when the reproducibility hash remains stable.
- The real-run output itself records that cross-machine byte replay is unverified: [provenance.json](viewer/provenance.json:76).

Can a stranger reproduce from the record alone? No. The record contains basenames, input hashes, grid, parameters and package version, but its input entries have no download URL: [provenance.py](src/microrelief/provenance.py:33). It also lacks the AOI geometry, Git commit/source digest, and GDAL/libdeflate environment identity. The reproducibility hash covers package version, grid, parameters, item IDs and input hashes—not the implementation itself: [provenance.py](src/microrelief/provenance.py:109).

Does CC-BY attribution reach the consumer? Yes for the exported GeoTIFFs and provenance sidecar:

- The attribution string includes DGT, CC BY 4.0 and the non-endorsement notice: [provenance.py](src/microrelief/provenance.py:22).
- It is attached inside the loop that writes every raster: [export.py](src/microrelief/export.py:39), [export.py](src/microrelief/export.py:47).
- A test independently opens every band and verifies the tag: [test_export.py](tests/test_export.py:143).
- It is also in the committed sidecar: [provenance.json](viewer/provenance.json:14).

The repository does not establish that attribution is embedded inside the standalone viewer PNG files.

> `return(s) fall outside its declared footprint ... this is a corrupted read, not a property of the terrain — refusing rather than publishing a density divided by an exploded bounding box`

Code: [read.py](src/microrelief/read.py:128).  
Exercised by the regression test at [test_read.py](tests/test_read.py:188).

## README contradictions

I found one clear contradiction with the published product:

- The opening says an interpolated cell is “interpolated from a named neighbour”: [README.md](README.md:3). Internally, `BasisResult` does hold the source row and column: [density.py](src/microrelief/density.py:24). But the exported raster list contains only DTM, DSM, CHM, basis, `n_all`, and `n_ground_asprs`: [surfaces.py](src/microrelief/surfaces.py:25). The source indices are used to construct the DTM and then discarded: [surfaces.py](src/microrelief/surfaces.py:52). Thus the consumer can see that a cell was interpolated, but cannot identify the “named neighbour” from the published outputs.

Separately, the README’s reproduction commands are not sufficient “from the record alone”: the provenance lacks acquisition URLs, AOI geometry and an exact code/environment identity. The README does acknowledge that the LAZ download is manual, so this is a limitation of the reproduction presentation rather than a direct factual contradiction.
