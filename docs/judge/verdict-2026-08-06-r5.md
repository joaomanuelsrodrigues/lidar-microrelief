## 1. Ground filtering

The pipeline uses a progressive morphological filter over the per-cell minimum elevation surface:

> “A progressive morphological filter … open the minimum surface with windows of growing size” — [ground.py:1](src/microrelief/ground.py:1)

For each window, it performs a grey-scale opening and rejects cells whose elevation above the opened surface exceeds:

\[
\min(slope\_threshold \times window\_m + elevation\_threshold,\ max\_elevation)
\]

This is implemented at [ground.py:87](src/microrelief/ground.py:87).

The recorded parameters are:

- Cell: `0.5 m`
- `max_window_m = 4.0`
- `slope_threshold = 0.3`
- `elevation_threshold_m = 0.3 m`
- `max_elevation_m = 3.0 m`

They appear in [provenance.json:84](viewer/provenance.json:84). At 0.5 m resolution, `max_window_m=4` actually produces 1.5, 2.5, and 4.5 m windows; the parameter is a radius-search ceiling, not a literal maximum width ([ground.py:55](src/microrelief/ground.py:55), [test_ground.py:94](tests/test_ground.py:94)).

Why those values:

- `slope_threshold=0.3` and `elevation_threshold_m=0.3` are literature-derived but explicitly uncalibrated ([CALIBRATIONS.md:15](CALIBRATIONS.md:15)).
- `max_window_m=4.0` is an unmeasured object-scale default, producing the schedule above ([CALIBRATIONS.md:14](CALIBRATIONS.md:14)).
- `max_elevation_m=3.0` is intended to preserve 1.5 m terrace risers by allowing up to two risers; the synthetic test shows terrace preservation at 3.0 m and damage when the cap is reduced below one riser ([CALIBRATIONS.md:17](CALIBRATIONS.md:17), [test_ground.py:56](tests/test_ground.py:56)).
- `cell=0.5 m` matches the finest DGT published product but is still listed as uncalibrated for this site ([CALIBRATIONS.md:8](CALIBRATIONS.md:8)).

Agreement is computed per occupied cell, with official ground defined as at least one ASPRS class-2 return ([ground.py:137](src/microrelief/ground.py:137)):

| Metric | Result | Majority-class null |
|---|---:|---:|
| Ground recall | 0.9992618534 | 0.5034972851 |
| Non-ground recall | 0.4953807915 | 0.5034972851 |
| Overall accuracy | 0.7490835382 | 0.5034972851 |

Reported at [provenance.json:2](viewer/provenance.json:2). The null is the larger of official ground prevalence and its complement ([ground.py:150](src/microrelief/ground.py:150)). Thus ground performance is extremely high, but non-ground discrimination is slightly worse than the approximately 50.35% majority baseline.

## 2. Common grid

The grid is defined once by `grid_for_bounds()` in [grid.py:65](src/microrelief/grid.py:65). It snaps the AOI outward to cell boundaries and constructs one immutable `Grid`; the recorded instance is 3960 × 3960, 0.5 m, EPSG:3763 ([provenance.json:19](viewer/provenance.json:19)).

Each tile’s points are immediately converted to indices in that grid:

> `row, col, inside = self.grid.cell_indices(batch.x, batch.y)` — [accumulate.py:96](src/microrelief/accumulate.py:96)

Only common-grid aggregates survive each `add()` call ([accumulate.py:72](src/microrelief/accumulate.py:72)). There is no per-tile raster/window data structure. The order-independence test pours two tile halves into the same accumulator in opposite orders and obtains identical counts and elevations ([test_accumulate.py:31](tests/test_accumulate.py:31)).

All published bands are created with `grid.shape` ([surfaces.py:37](src/microrelief/surfaces.py:37)), and a test checks every raster against that one shape ([test_surfaces.py:98](tests/test_surfaces.py:98)). The only elementwise subtraction, `mds - mdt`, therefore occurs between arrays already constructed on the common AOI grid ([surfaces.py:62](src/microrelief/surfaces.py:62)).

That is strong structural evidence that elementwise arithmetic between per-tile windows cannot occur: per-tile windows are never constructed.

## 3. Voids

The output reports:

- Measured: `0.7460224722` — 74.6022%
- Interpolated: `0.2520743419` — 25.2074%
- Undetermined: `0.0019031859` — 0.1903%

See [provenance.json:27](viewer/provenance.json:27).

The classifications are defined as follows:

- Measured: the filter says ground and the cell has at least `k_min_returns`.
- Interpolated: not measured, but a measured cell is within 2 m.
- Undetermined: neither condition holds.

Implementation: [density.py:56](src/microrelief/density.py:56).

The closed-form Poisson expectation is:

\[
P(N=0)=e^{-\lambda},
\qquad
\lambda=\rho c^2 f
\]

as implemented at [precheck.py:34](src/microrelief/precheck.py:34).

The report uses measured density \(\rho=26.9902122232\) pts/m², cell size \(c=0.5\) m, and reference ground fraction \(f=1\):

\[
e^{-26.9902122232(0.5)^2}
=e^{-6.7475530558}
=0.0011737482
\]

That is 0.117375% expected empty cells, recorded at [provenance.json:28](viewer/provenance.json:28). The code explicitly describes \(f=1\) as a reference comparison, not a measured canopy ground-return fraction ([density.py:87](src/microrelief/density.py:87)).

## 4. Provenance and reproducibility

Do two runs produce identical bytes? Qualified yes for the six raster bands on the two clean real-data runs present in the workspace: every `outputs/*.tif` SHA-256 matched its `outputs_replay/*.tif` counterpart. A synthetic test also explicitly requires two exports to be byte-identical ([test_export.py:152](tests/test_export.py:152)).

But:

- The two `provenance.json` sidecars are not byte-identical because `created_utc` changes. The timestamp is generated at [provenance.py:124](src/microrelief/provenance.py:124) and deliberately excluded from the reproducibility hash.
- `outputs2` differs in all six raster hashes, consistent with the recorded unstable/corrupted read.
- Cross-machine byte identity is expressly unverified ([provenance.json:76](viewer/provenance.json:76)).

Can a stranger reproduce from the record alone? No. The record contains input names and SHA-256 digests ([provenance.json:34](viewer/provenance.json:34)), grid, parameters, and package version, but it contains no download URL/provider asset identifier sufficient to acquire the bytes and no source commit or source-tree digest. The reproducibility hash covers only package version, grid, parameters, item IDs, and input hashes ([provenance.py:109](src/microrelief/provenance.py:109)). Therefore it can verify suitably obtained inputs/configuration, but cannot independently provide them or uniquely identify the executed code.

Does CC-BY attribution reach the consumer? Yes for every exported GeoTIFF and the sidecar. `export()` writes `provenance.attribution` into every raster’s metadata ([export.py:39](src/microrelief/export.py:39)); the test checks every band ([test_export.py:143](tests/test_export.py:143)). Direct inspection of all six available `outputs/*.tif` files also found the full DGT/CC BY 4.0 attribution. It is present in the sidecar at [provenance.json:14](viewer/provenance.json:14).

## 5. Three demonstrated refusals

1. Tile without a declared CRS:

   > `"{path.name} declares no CRS; refusing to assume one"` — [read.py:69](src/microrelief/read.py:69)

2. Tile without any official ASPRS class-2 ground returns:

   > `"no points carry ASPRS class 2; without an official ground class there is nothing to compare our own filter against"` — [read.py:116](src/microrelief/read.py:116)

3. Selection spanning multiple sorties:

   > `"a mosaic of two epochs is a product made of two moments — pass allow_mixed_epochs to accept and declare it"` — [tiles.py:300](src/microrelief/tiles.py:300)

Other explicit refusals include non-finite coordinates ([read.py:108](src/microrelief/read.py:108)), returns outside the catalogue footprint ([read.py:137](src/microrelief/read.py:137)), partial AOI coverage ([tiles.py:307](src/microrelief/tiles.py:307)), mixed CRS ([tiles.py:266](src/microrelief/tiles.py:266)), and an oversized grid ([grid.py:84](src/microrelief/grid.py:84)).
