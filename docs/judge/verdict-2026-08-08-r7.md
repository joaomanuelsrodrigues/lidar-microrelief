## 1. Ground filtering

The pipeline uses a progressive morphological filter over the per-cell minimum elevation surface:

> “A progressive morphological filter (Zhang et al. 2003…)” — [ground.py](src/microrelief/ground.py:3)

For progressively doubled radii, it applies a grey opening and rejects cells whose elevation above the opening exceeds:

\[
\min(slope\_threshold \times window_m + elevation\_threshold_m,\ max\_elevation_m)
\]

This is implemented at [ground.py](src/microrelief/ground.py:87).

The recorded run used:

- `cell = 0.5 m`
- `max_window_m = 4.0`
- `slope_threshold = 0.3`
- `elevation_threshold_m = 0.3 m`
- `max_elevation_m = 3.0 m`

See [provenance.json](viewer/provenance.json:84). At 0.5 m, the actual window widths are 1.5, 2.5, and 4.5 m; `max_window_m` is a radius-search ceiling, not an actual window width ([ground.py](src/microrelief/ground.py:55), [test_ground.py](tests/test_ground.py:94)).

Why those values:

- The repository explicitly labels every one of these thresholds as uncalibrated: [provenance.json](viewer/provenance.json:94).
- `slope_threshold=0.3` and `elevation_threshold_m=0.3` are literature-derived starting values, not site calibration ([CALIBRATIONS.md](CALIBRATIONS.md:15)).
- `max_window_m=4.0` is an unmeasured object-scale default ([CALIBRATIONS.md](CALIBRATIONS.md:14)).
- `max_elevation_m=3.0` was chosen to tolerate two 1.5 m synthetic terrace risers, but its stated calibration target—largest real riser at the site—was not measured ([CALIBRATIONS.md](CALIBRATIONS.md:17)). The synthetic test retains all five levels at 3 m and loses one when the cap is reduced to 1 m ([test_ground.py](tests/test_ground.py:39), [test_ground.py](tests/test_ground.py:56)).
- `cell=0.5 m` matches the finest DGT product, but the site-specific terrace-width calibration target is still outstanding ([CALIBRATIONS.md](CALIBRATIONS.md:8)).

Agreement is computed per measured cell against whether that cell contains any official ASPRS class-2 return ([ground.py](src/microrelief/ground.py:137)). The committed output reports:

| Metric | Result | Majority-class null |
|---|---:|---:|
| Ground recall | 0.9992618534 | 0.5034972851 |
| Non-ground recall | 0.4953807915 | 0.5034972851 |
| Overall accuracy | 0.7490835382 | 0.5034972851 |

Source: [provenance.json](viewer/provenance.json:2). The confusion counts are TP 7,809,752; FN 5,769; TN 3,817,874; FP 3,889,074.

## 2. Common grid

The run’s grid is constructed once from the AOI at [cli.py](src/microrelief/cli.py:215). Its snapping and dimensions are defined in `grid_for_bounds()` at [grid.py](src/microrelief/grid.py:65).

The recorded grid is 3960 × 3960, 0.5 m, EPSG:3763, origin `(-20990, 256990)` ([provenance.json](viewer/provenance.json:19)).

There are no per-tile raster windows to combine:

- One `Accumulator` allocates arrays of `grid.n_cells` ([accumulate.py](src/microrelief/accumulate.py:81)).
- Each tile’s coordinates are immediately converted to indices in that grid ([accumulate.py](src/microrelief/accumulate.py:91)).
- Only global per-cell extrema and counts survive each call ([accumulate.py](src/microrelief/accumulate.py:103)).
- The only elementwise cross-surface arithmetic, CHM = DSM − DTM, is performed after accumulation on arrays of `grid.shape` ([surfaces.py](src/microrelief/surfaces.py:48), [surfaces.py](src/microrelief/surfaces.py:64)).
- The test splits a cloud into two “tiles,” reverses their ingestion order, and obtains identical global counts and minima ([test_accumulate.py](tests/test_accumulate.py:31)).
- Every published band is asserted to have the common grid shape ([test_surfaces.py](tests/test_surfaces.py:98)).

Within the repository’s implementation, this shows that elementwise arithmetic cannot occur between per-tile windows because such windows are never created.

## 3. Voids

The committed output reports:

- Measured: `0.7460224722` = **74.6022%**
- Interpolated: `0.2520743419` = **25.2074%**
- Undetermined: `0.0019031859` = **0.1903%**

See [provenance.json](viewer/provenance.json:27).

“Measured” means the filter called the cell ground and it contains at least `k_min_returns`; non-measured cells are interpolated only if a measured cell is within 2 m ([density.py](src/microrelief/density.py:63)).

The closed-form null is Poisson emptiness:

\[
P(N=0)=e^{-\lambda},\qquad
\lambda=\rho c^2 f
\]

implemented at [precheck.py](src/microrelief/precheck.py:34). The honesty report fixes \(f=1\), explicitly treating it as the null where every return reaches ground ([density.py](src/microrelief/density.py:91)).

With \(\rho=26.9902122232\ \mathrm{pts/m^2}\) and \(c=0.5\ \mathrm m\):

\[
e^{-26.9902122232(0.5)^2}
=0.0011737482
= \mathbf{0.117375\%}.
\]

Those inputs and the resulting value are recorded at [provenance.json](viewer/provenance.json:28).

## 4. Provenance and reproducibility

Do two runs produce identical bytes? **Only in limited circumstances.**

A synthetic same-machine test exports twice and compares SHA-256 hashes of every GeoTIFF byte-for-byte ([test_export.py](tests/test_export.py:152)). Golden output bytes are also pinned, but the test explicitly says those bytes depend on local GDAL/libdeflate builds and cross-machine replay is unverified ([test_export.py](tests/test_export.py:198)).

For the real dataset, the answer is **not established**: two reads were byte-identical, one produced a corrupted coordinate, and one failed with an I/O error ([live-smoke.md](docs/live-smoke.md:204)). The provenance itself records: “Byte-identical replay is verified on one machine only; cross-machine replay is unverified” ([provenance.json](viewer/provenance.json:76)).

Can a stranger reproduce from the record alone? **No.** The code itself calls the record a “verification anchor, not a self-contained recipe” because it omits the acquisition route and exact code revision ([provenance.py](src/microrelief/provenance.py:1)). It contains input filenames and hashes, grid, parameters, and package version, but not input URLs or immutable source revision ([provenance.py](src/microrelief/provenance.py:112)).

The hash also cannot detect code changes unless the developer bumps `__version__`; a documented run before and after a code change produced the same hash over different bytes ([live-smoke.md](docs/live-smoke.md:195)).

Does CC-BY attribution reach the consumer? **Yes, for every exported GeoTIFF and the provenance sidecar.** The attribution text is defined at [provenance.py](src/microrelief/provenance.py:25), inserted into every raster’s tags at [export.py](src/microrelief/export.py:39), and tested for every band at [test_export.py](tests/test_export.py:143). It is also present in the committed sidecar at [provenance.json](viewer/provenance.json:14).

## README contradictions

I found no unresolved numerical contradiction between the README and the final committed output. Its grid, basis fractions, void expectation, agreement values, confusion count, hash, attribution, and replay limitations agree with `viewer/provenance.json` and the corrected live-smoke record.

One statement requires careful qualification but is not ultimately contradictory: the README calls the surfaces re-derived from “raw returns,” while code removes official ASPRS noise classes 7 and 18 before forming the minimum surface ([read.py](src/microrelief/read.py:123)). The README itself discloses that preprocessing at [README.md](README.md:75), so it does not conceal or contradict the implementation.
