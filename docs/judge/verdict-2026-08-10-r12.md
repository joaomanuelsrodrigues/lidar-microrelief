## 1. Ground filtering

The pipeline uses a progressive morphological filter over the per-cell minimum elevation surface. The implementation repeatedly applies a grey-scale morphological opening with exponentially increasing radii, rejecting cells whose elevation above the opened surface exceeds a slope-dependent, capped tolerance:

- Filter identification: [ground.py:1](src/microrelief/ground.py:1)
- Increasing-radius loop and opening: [ground.py:87](src/microrelief/ground.py:87)
- Tolerance formula: [ground.py:90](src/microrelief/ground.py:90)
- Final ground decision: [ground.py:95](src/microrelief/ground.py:95)

The recorded parameters are:

| Parameter | Value | Repository evidence for why |
|---|---:|---|
| `max_window_m` | 4.0 m | The radius doubles, producing actual widths 1.5, 2.5, and 4.5 m at 0.5 m cells; the parameter is a ceiling, not an actual window width: [ground.py:46](src/microrelief/ground.py:46), [ground.py:55](src/microrelief/ground.py:55). It remains explicitly uncalibrated: [provenance.json:94](viewer/provenance.json:94), [provenance.json:98](viewer/provenance.json:98). No empirical reason for choosing exactly 4.0 is established by code/output. |
| `slope_threshold` | 0.3 | Used as `slope_threshold × window_m`: [ground.py:91](src/microrelief/ground.py:91). The record explicitly calls it uncalibrated: [provenance.json:95](viewer/provenance.json:95), [provenance.json:104](viewer/provenance.json:104). Therefore why exactly 0.3 is not answerable from code/output. |
| `elevation_threshold_m` | 0.3 m | It is the additive tolerance term: [ground.py:91](src/microrelief/ground.py:91). It is also explicitly uncalibrated: [provenance.json:91](viewer/provenance.json:91), [provenance.json:101](viewer/provenance.json:101). Why exactly 0.3 is not established. |
| `max_elevation_m` | 3.5 m | This caps every tolerance and therefore controls whether risers survive: [ground.py:75](src/microrelief/ground.py:75), [ground.py:91](src/microrelief/ground.py:91). Unlike the others, it is deliberately absent from the uncalibrated list: [cli.py:33](src/microrelief/cli.py:33). |

Official agreement is computed per measured cell, with “official ground” meaning at least one ASPRS class-2 return in that cell: [ground.py:137](src/microrelief/ground.py:137), [ground.py:141](src/microrelief/ground.py:141).

## 2. Common grid

The common grid is created once from the full AOI bounds:

- Grid snapping and dimensions: [grid.py:73](src/microrelief/grid.py:73)
- Runtime construction before reading tiles: [cli.py:293](src/microrelief/cli.py:293), [cli.py:300](src/microrelief/cli.py:300)
- Recorded real grid: origin `(-20990, 256990)`, 3960 × 3960, 0.5 m, EPSG:3763: [viewer/provenance.json:19](viewer/provenance.json:19)

There are no per-tile raster windows in the processing path. Each tile’s points are mapped directly into the same grid indices, and only global per-cell aggregates are retained:

- One `Accumulator(grid)` owns arrays sized to `grid.n_cells`: [accumulate.py:72](src/microrelief/accumulate.py:72), [accumulate.py:81](src/microrelief/accumulate.py:81)
- Each batch maps through that grid: [accumulate.py:91](src/microrelief/accumulate.py:91)
- Tile results are merged into the global arrays at cell indices: [accumulate.py:100](src/microrelief/accumulate.py:100), [accumulate.py:103](src/microrelief/accumulate.py:103)
- The CLI reads each tile and immediately adds it to that accumulator: [cli.py:244](src/microrelief/cli.py:244), [cli.py:259](src/microrelief/cli.py:259)
- Only after all tiles are accumulated does it call `finish`, classify, and build surfaces: [cli.py:304](src/microrelief/cli.py:304)

The relevant elementwise surface arithmetic—CHM = DSM − DTM—is between arrays already built on that one grid: [surfaces.py:62](src/microrelief/surfaces.py:62). Exports likewise take shape, transform, and CRS from the common `Grid`: [export.py:60](src/microrelief/export.py:60).

Therefore the code structurally precludes arithmetic between per-tile windows: such windows are never constructed or retained.

## 3. Voids

The committed full-resolution record reports:

- **Measured:** `0.7460224722` = **74.6022%**
- **Interpolated:** `0.2520743419` = **25.2074%**
- **Undetermined:** `0.0019031859` = **0.1903%**

Source: [viewer/provenance.json:27](viewer/provenance.json:27).

The states are computed by counting the three basis codes over the common grid: [density.py:94](src/microrelief/density.py:94). A cell is measured only if the filter calls it ground and it has the minimum number of returns; otherwise it is interpolated only when a measured neighbour lies within 2 m: [density.py:65](src/microrelief/density.py:65), [density.py:70](src/microrelief/density.py:70), [density.py:77](src/microrelief/density.py:77).

The closed-form model is

\[
P(N=0)=e^{-\lambda},\qquad
\lambda=\rho c^2 f
\]

as implemented at [precheck.py:51](src/microrelief/precheck.py:51). For the honesty report, `f = 1`: [density.py:91](src/microrelief/density.py:91).

Using the recorded density \(\rho=26.9902122232\) points/m² and cell size \(c=0.5\) m:

\[
e^{-26.9902122232(0.5)^2}
= e^{-6.7475530558}
= 0.0011737482
\]

or **0.1173748%**. That exact result is recorded at [viewer/provenance.json:28](viewer/provenance.json:28).

This is an open-ground/“every return reaches ground” reference model, not a prediction of the observed basis states. The record says so explicitly: [viewer/provenance.json:82](viewer/provenance.json:82).

## 4. Provenance and reproducibility

**Do two runs produce identical bytes?** Qualified answer:

- A synthetic test establishes byte-identical GeoTIFFs when the same surfaces and the same provenance object are exported twice: [test_export.py:177](tests/test_export.py:177).
- Two real 0.3.0 passes were byte-identical across all six bands, but their provenance files differed in `created_utc`: [live-smoke.md:323](docs/live-smoke.md:323), [live-smoke.md:344](docs/live-smoke.md:344).
- This is not a general stability guarantee. The committed record reports an earlier corrupted read and an outright failed read, with cross-machine replay still unverified: [viewer/provenance.json:79](viewer/provenance.json:79).
- Across package versions, byte identity is deliberately not expected because version and reproducibility hash are written into TIFF tags. The 0.3.0→0.4.0 check therefore found identical cell values, not identical files: [live-smoke.md:368](docs/live-smoke.md:368), [live-smoke.md:443](docs/live-smoke.md:443).

So: **yes for controlled same-version clean runs; no unconditional byte-reproducibility claim is established.**

**Can a stranger reproduce from the record alone?** No. The record provides filenames, SHA-256 digests, grid, parameters, version, and results, but no acquisition route and no exact source-code revision. The module itself explicitly calls it “a verification anchor, not a self-contained recipe”: [provenance.py:3](src/microrelief/provenance.py:3). The input entries confirm that they contain basenames and hashes, not download locations: [viewer/provenance.json:34](viewer/provenance.json:34). Code changes reach the hash only through the manually maintained package version: [provenance.py:116](src/microrelief/provenance.py:116).

**Does CC-BY attribution reach the consumer?** Yes for exported artifacts:

- Attribution is mandatory and empty attribution is refused: [provenance.py:101](src/microrelief/provenance.py:101).
- It is stored in the committed provenance: [viewer/provenance.json:14](viewer/provenance.json:14).
- Export copies it into every TIFF’s tags: [export.py:45](src/microrelief/export.py:45), [export.py:53](src/microrelief/export.py:53), [export.py:75](src/microrelief/export.py:75).
- A test opens every exported band independently and verifies that its attribution contains `CC BY 4.0`: [test_export.py:143](tests/test_export.py:143).
