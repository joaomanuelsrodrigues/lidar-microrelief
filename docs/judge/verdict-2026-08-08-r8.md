1. Ground filtering

The pipeline uses a progressive morphological filter over the per-cell minimum elevation surface:

> “A progressive morphological filter … open the minimum surface with windows of growing size and mark as object any cell that the opening pushes down further than a slope-dependent tolerance allows.”  
> [ground.py:1](src/microrelief/ground.py:1)

For each growing window, the implemented threshold is:

```text
min(slope_threshold × window_width + elevation_threshold,
    max_elevation)
```

This is implemented at [ground.py:87](src/microrelief/ground.py:87).

The recorded parameters are:

- Cell: `0.5 m`
- `max_window_m = 4.0`
- Actual windows: `1.5, 2.5, 4.5 m`
- `slope_threshold = 0.3`
- `elevation_threshold_m = 0.3 m`
- `max_elevation_m = 3.0 m`

The values appear in the run record at [provenance.json:84](viewer/provenance.json:84). The actual window schedule follows from the doubling-radius implementation at [ground.py:46](src/microrelief/ground.py:46) and [ground.py:55](src/microrelief/ground.py:55).

Why those values:

- `0.5 m` matches the finest DGT published product.
- `4.0 m` is an unmeasured search-radius ceiling, not an actual window width.
- Both `0.3` thresholds are explicitly unmeasured starting values, not Zhang et al.’s values.
- The `0.3 m` elevation threshold sits at the edge of the cited 0.2–0.3 m measurement-error band.
- `3.0 m` is intended to preserve terrace risers by capping all tolerances, but the repository explicitly says the largest real site riser still needs measurement.

These qualifications are recorded at [CALIBRATIONS.md:8](CALIBRATIONS.md:8) and [CALIBRATIONS.md:14](CALIBRATIONS.md:14).

Agreement is computed only over cells containing returns, with official ground defined as at least one ASPRS-ground return; the confusion matrix and majority-class null are calculated at [ground.py:137](src/microrelief/ground.py:137).

Recorded results:

| Metric | Filter | Majority-class null |
|---|---:|---:|
| Ground recall | 0.9992619 | 0.5034973 |
| Non-ground recall | 0.4953808 | 0.5034973 |
| Overall accuracy | 0.7490835 | 0.5034973 |

The exact values and confusion counts are at [provenance.json:2](viewer/provenance.json:2). The null is an accuracy baseline, not technically a per-class recall baseline; the repository does not calculate separate per-class majority-null values.

2. Common grid

`Grid` and `grid_for_bounds` define the common grid at [grid.py:22](src/microrelief/grid.py:22) and [grid.py:65](src/microrelief/grid.py:65). Bounds are snapped outward using floor/ceil at lines 79–82.

The recorded grid is one `3960 × 3960`, `0.5 m`, EPSG:3763 grid with origin `(-20990, 256990)`: [provenance.json:19](viewer/provenance.json:19).

The run constructs it once, passes it to `_read_inputs`, finishes that accumulator, and builds every downstream surface from the resulting common-grid statistics:

> `grid = grid_for_bounds(...)`  
> `acc, ... = _read_inputs(paths, grid, ...)`  
> `stats = acc.finish()`  
> `surfaces = build_surfaces(grid, stats, basis)`

See [cli.py:208](src/microrelief/cli.py:208).

No per-tile raster windows are created. Each tile is immediately reduced into arrays indexed by the common grid; only minima, maxima and counts survive between calls: [accumulate.py:72](src/microrelief/accumulate.py:72). Updates are common-cell operations such as:

> `self._min_all[cells] = np.minimum(self._min_all[cells], mins)`

at [accumulate.py:103](src/microrelief/accumulate.py:103).

Thus the code contains tile-to-common-grid accumulation, but no pair of per-tile raster windows upon which elementwise arithmetic could operate.

3. Voids

The recorded fractions are:

- Measured: `0.7460224722` — 74.602%
- Interpolated: `0.2520743419` — 25.207%
- Undetermined: `0.0019031859` — 0.190%

See [provenance.json:27](viewer/provenance.json:27).

A measured cell must be accepted by the ground filter and contain at least `k_min_returns`; other cells are interpolated only if a measured cell is within `2.0 m`, otherwise they remain undetermined: [density.py:56](src/microrelief/density.py:56).

The implemented closed form is:

\[
P(N=0)=e^{-\lambda},\qquad
\lambda=\rho c^2 f
\]

See [precheck.py:34](src/microrelief/precheck.py:34).

The honesty report deliberately uses `f = 1`: [density.py:87](src/microrelief/density.py:87). With recorded density `ρ = 26.9902122 pts/m²` and `c = 0.5 m`:

\[
e^{-26.9902122(0.5)^2}
= e^{-6.747553}
= 0.001173748
\]

Therefore the expectation is `0.1173748%` empty cells, as recorded at [provenance.json:27](viewer/provenance.json:27). It is an all-returns-reach-ground null, not a prediction using the observed ground-return fraction.

4. Provenance and reproducibility

Do two runs produce identical bytes? Only with qualifications.

- Synthetic exports using the same already-built provenance object are tested byte-identical for every GeoTIFF band: [test_export.py:152](tests/test_export.py:152).
- Independently built complete outputs are not byte-identical as a whole because `created_utc` changes. The timestamp is generated at [provenance.py:130](src/microrelief/provenance.py:130), and the test confirms JSON timestamps differ while only the reproducibility hash remains equal: [test_provenance.py:34](tests/test_provenance.py:34).
- On real data, byte-stable replay is not established: two reads were clean and byte-identical, one produced a corrupted coordinate, and one failed with `IoError`. That recorded observation is at [live-smoke.md:204](docs/live-smoke.md:204).
- Cross-machine replay is explicitly unverified in the output record: [provenance.json:76](viewer/provenance.json:76).

Can a stranger reproduce from the record alone? No. The code itself describes the record as “not a self-contained recipe”: it omits the acquisition route and exact code revision, at [provenance.py:1](src/microrelief/provenance.py:1). Input records contain basenames and hashes but no source URLs: [provenance.py:38](src/microrelief/provenance.py:38). The hash also sees code changes only through a manually maintained version: [provenance.py:114](src/microrelief/provenance.py:114).

Does CC-BY attribution reach the consumer? For products delivered through the implemented paths, yes:

- Every exported GeoTIFF gets the attribution tag: [export.py:39](src/microrelief/export.py:39) and [export.py:63](src/microrelief/export.py:63).

A detached viewer PNG itself has no demonstrated embedded attribution; attribution reaches that consumer through the accompanying HTML and JSON.
